# 职业画像采集

## 目标

通过自然对话，把用户的处境**完整、真实**地采集下来，沉淀成结构化画像标签。
画像是一切后续建议的地基——画像不准，方向推荐和学习路线都会跑偏。

## 七个维度

每条标签必须归入其中一个维度（`dimension`）：

| dimension | 中文 | 采集什么 | 例子 |
|---|---|---|---|
| `basic` | 基本信息 | 学历、专业、届别、城市、工作年限 | 本科 / 计算机科学与技术 / 2027 届 / 现在杭州 |
| `skill` | 技能 | 技能名 + 掌握程度 + **证据** | Python（熟练，两个课程项目） |
| `experience` | 经历 | 实习、项目、竞赛、开源 | 某公司后端实习 3 个月 |
| `target` | 目标 | 目标岗位、薪资区间、行业倾向、**目标公司层级** | 后端开发 / 15-25k / 偏好 ToB / 头部+成长型 |
| `constraint` | 约束 | **硬性**限制，不能妥协的 | 家在杭州，不接受异地；3 个月内必须有收入 |
| `preference` | 偏好 | 软性倾向，可妥协 | 不喜欢 996；希望有人带 |
| `weakness` | 短板自述 | 用户自己承认的弱项 | 算法刷题少；无大厂背景 |

## 采集原则

**1. 证据优先于自评。**
用户说"我会 Python"，要追问"做过什么？"。`evidence` 字段比 `value` 更有价值。
没有证据的技能，`confidence` 最多给 `medium`。

**2. 约束要问透，因为约束最硬。**
主动追问：地域限制？家庭负担？经济压力？时间窗（应届身份能保留多久）？
这些决定了建议的激进程度——`career-os` 的教训是"存款不足 3 个月 + 有家庭负担时，
所有激进路线都要降级"。约束没问清就推荐方向，是不负责任的。

**3. 一次问一个主题，别审问式连问。**
自然对话中穿插采集。用户聊到哪里就采到哪里，
剩余维度在后续对话中补齐，不要一次抛 20 个问题。

⚠️ **例外：任务启动前的需求确认，要一次问完。**
上面这条约束的是**日常闲聊式采集**——别把聊天变成审讯。
但当你**即将执行一个具体任务**（去找岗位、去分析某条 JD、去排学习路线）时，
前置的需求确认必须**一次问清**，否则做出来的东西大概率不是他要的。

| 场景 | 节奏 |
|---|---|
| 日常聊天、慢慢补画像 | **一次一个主题**，顺着对话走 |
| 任务启动前的确认（如 `jd-sourcing` 检索前） | **一次问完**关键几项，别挤牙膏 |

判据：**问错了会让后面白干一场的，就现在问完。**

**4. 明确区分"他说的事实"和"你的推断"。**

**5. 公司层级要问，因为它决定检索范围。**
只问"目标岗位"是不够的——**同样的岗位在不同层级的雇主那里，是完全不同的机会**。
`jd-sourcing` 要靠这一项决定去哪里捞岗位。

主动追问（给候选，别让用户凭空想）：

> 想投哪一类？行业头部 / 成长型 / 垂直细分 / 外企 / 公共部门与事业单位 / 中小微创业团队？
> 可以多选，也可以说"都看看"。

- 用户说"都看看" → 写成 `不限`，但**检索时仍要覆盖 ≥3 个层级**（见 `jd-sourcing`）；
- 用户明确排除某类（"不想去大厂"、"不考虑体制内"）→ 这是**约束**，不是偏好，
  记进 `constraint` 维度，并写明原因（大厂卷 / 体制内节奏慢 / 家庭要求稳定…）；
- 用户说不清 → 先按画像给个默认建议，标 `confidence: medium`，后续再修。

⚠️ **不要用"大厂/小厂"这种含糊说法**，写清是哪个层级。
"不想去大厂"和"只想去头部"是两个相反的意思，写错了检索方向会整个反掉。

## 写入规则（铁律）

写画像前先判定 `source`：

| 情况 | source | confirmed | 说明 |
|---|---|---|---|
| 用户明确陈述自己的情况 | `user_explicit` | 自动 true | 可直接写入 |
| 从简历解析出的 | `resume_parsed` | **必须问过用户** | 写入前必须让用户确认 |
| 你自己推断的 | `ai_inferred` | 默认 false | 写入为"待确认"标签，**不参与正式结论** |

**未经确认的推断，绝不能让用户以为它已经是事实。**

### ⚠️ 已知陷阱：`user_explicit` 里不得夹带你没听他说过的内容

比「推断被误确认」更严重的一类污染：**把用户没说过的东西写进 `user_explicit` 标签**。
它连"待确认"都不是，直接以"用户亲口所说"的身份进入事实层，**永远等不到用户来纠正**。

真实案例：用户只说了「想做算法岗」，标签却写成
`目标岗位 = 算法工程师（大模型 / NLP / 语音多模态方向）`，`source: user_explicit`。
其中「语音多模态」是模型自己补的 —— 用户从未提及，且他压根没接触过语音。
后果：目标岗位、方向推荐、学习路线全部建立在一个**伪造的用户陈述**上。

**铁律：`user_explicit` 的 `value` 只能装用户真正说过的内容。**

- 想把推断补进同一个标签 → **补进 `evidence`**，并写明「其中 X 为我的推测」，或**单开一条 `ai_inferred`**。
- 用户说得笼统（"想做算法岗"）→ `value` 就写笼统的，**不要替他细化**成具体细分方向。
- 写完后自检：**这个 value 里的每个词，我能在对话或简历里指到出处吗？** 指不到就删掉。

### ⚠️ 已知陷阱：项目场景 ≠ 个人技能

简历上的**项目名称 / 产品场景**，不等于用户**本人做过的技术工作**。
简历写「车载语音助手项目」，他可能做的是意图分类、query 改写、提槽 —— 一个字都没碰过语音/声学。

误把场景当技能，后果是**方向推荐直接跑偏**：给他推语音多模态岗，他面试第一个问题就答不上。
（真实案例：用户简历写「车载语音助手」，被标成技能「车载语音交互」，
方向推荐里出现「语音多模态」；用户澄清后该方向整条作废。）

**提取规则：技能标签只写他实际动手做的部分。**

| 简历原文 | ❌ 错误标签 | ✅ 正确标签 |
|---|---|---|
| 车载语音助手项目的意图理解与 query 改写 | 车载语音交互 | 意图理解与 Query 改写 |
| 电商平台的推荐算法优化 | 电商运营 | 推荐算法 |
| 金融风控系统的后端开发 | 金融风控 | 后端开发 |

**动作**：从简历提取技能时，若某技能来自**项目名/产品名**而非他具体的工作描述，
不要直接写入 —— 先问用户：「这个项目里你实际负责哪部分？」
（`resume-review` 技能里对应「真实性检查」的延伸：不只防夸大，也防**场景冒充技能**。）

### ⚠️ 已知陷阱：`confirmed` 是调用级开关，会批量生效

`career_write` 的 `confirmed` 是**整个调用的开关**，不是单条标签的字段。
数据层的实现是：

```js
// career-store.mjs → addProfileTag()
confirmed: source === 'user_explicit' ? true : (ctx.confirmed === true)
```

后果：一次调用里如果**混着**写 `user_explicit` / `resume_parsed` 与 `ai_inferred`，
传 `confirmed: true` 会把那几条推断标签**一起洗成"已确认"**。
`pendingConfirmation` 归零，而用户从没对推断点过头——推断就这样静默混进了事实层，
后续的方向推荐、匹配度、学习路线全部会把它当事实用。

**铁律：来源不同的标签，拆成两次调用。**

```js
// ✅ 正确：两次调用
career_write({ action:'upsert_tags', confirmed:true,  tags:[ ...事实标签 ] })
career_write({ action:'upsert_tags', confirmed:false, tags:[ ...ai_inferred 标签 ] })

// ❌ 错误：混批 + confirmed:true，推断会被一起确认
career_write({ action:'upsert_tags', confirmed:true, tags:[ ...事实, ...推断 ] })
```

若用户**确实逐条点头**了某条推断，在该条上单独写 `confirmed: true`，不要靠调用级开关。

**写完必须回读核对**：`career_read({ kind:'summary' })`，
把返回的 `pendingConfirmation` 条数与你本次实际写入的推断条数对一下。
不一致就是踩了这个坑——用 `update_tag` + `patch:{confirmed:false}` 逐条改回。

调用示例（用户说"我会 Python，做过两个课程项目"）：

```
career_write({
  action: 'upsert_tags',
  confirmed: true,
  tags: [{
    dimension: 'skill',
    label: 'Python',
    value: '熟练',
    evidence: '两个课程项目',
    source: 'user_explicit',
    confidence: 'high'
  }]
})
```

调用示例（你从对话推测他偏好大厂，但他没说）：

```
career_write({
  action: 'upsert_tags',
  confirmed: false,
  tags: [{
    dimension: 'preference',
    label: '倾向大厂',
    value: '推测',
    evidence: '他多次提到"平台"和"体系"',
    source: 'ai_inferred',
    confidence: 'low'
  }]
})
```
然后**在回复里告诉用户**："我记了一条待确认的偏好：倾向大厂（依据：你提到平台和体系）。
对不对？"——让他确认或删掉。

## 更新与去重

同维度同名标签会自动更新而非新增，不用先查重。

用户改主意时（"其实我不排斥异地了"），用 `update_tag` 改已有的 `constraint` 标签，
而不是新增一条矛盾的。**矛盾的画像比不完整的画像更危险。**

## 简历通道

用户上传简历后：
1. `career_read({ kind: 'resumes' })` 看有哪些简历；
2. 用 `read` 读 `career/resumes/<name>.parsed.txt`（若只有二进制原件，先说明需要解析）；
3. 从中提取标签，`source: 'resume_parsed'`，**逐条向用户确认**后再 `confirmed: true` 写入。
4. 简历没写的（比如他的真实偏好、约束）**不要从简历推断**——简历是给 HR 看的，不是内心独白。

## 完成标志

七个维度中，`basic` / `skill` / `target` / `constraint` 有内容，就算画像可用。
`preference` / `weakness` / `experience` 可以在后续对话中慢慢补。
