# 面经检索与面试准备

## 目标

用户要准备面试时，最没用的回答是"建议复习基础、准备好项目介绍"。
有用的是：**这家公司这个岗位最近真实在面什么、几轮、哪一轮深挖什么**。

所以本技能的核心动作是**去网上找真实面经并读完**，而不是凭 JD 推理。
面经是唯一能回答"面试官实际会问什么"的证据。

## 铁律：面经必须真读到，不能编

**1. 没读到就说没读到。**
检索不到可靠面经，就直说"这几轮检索没找到"，然后**明确标注**改用 JD + 通用面试规律推理
（写成"以下是我的推断，不是面经"）。**绝不编造面试题、轮次、面试官风格**，
也绝不把 A 公司的面经挂到 B 公司名下。

**2. 每道题都要能指回来源。**
给出的任何一道真题/考点，都要能说出"来自第几篇、哪个链接、大概什么时间"。
指不出来源的，删掉，不要留在报告里充数。

**3. 面经是"别人那次面试"的过去时，不是这家公司的承诺。**
同公司不同部门、不同年份差异极大。结论要带限定：
"2025 校招某部门" ≠ "这家公司都这样"。

## 流程

```
1. career_read({ kind: 'profile', confirmedOnly: true })   ← 用户是谁、会什么
2. career_read({ kind: 'jobs', company: '<公司>' })         ← 目标 JD 原文 + businessSkills
3. 由 JD 的 businessSkills + skills 决定搜什么（§2）
4. web_search 多轮检索 → web_fetch 读最像面经的 3-5 篇原文（§3、§4）
5. 抽结构化摘要 + 交叉验证 + 时效标注（§5、§6）
6. 回接画像，给排序过的准备清单（§7、§8）
```

### 1. 定靶：先读画像和 JD

```
career_read({ kind: 'profile', confirmedOnly: true })   ← 已确认画像
career_read({ kind: 'jobs', company: '<公司>' })         ← 该公司在池子里的 JD
```

从 JD 里取三个检索锚点：

- **公司 + 岗位名**：用 JD 里的原始 `title`，不要自己改写成"大模型工程师"之类；
- **城市 / 部门业务线**：描述里常带（如"某事业群""XX 实验室"），能大幅收窄到具体团队；
- **`businessSkills` 标签**：见下。

池子里没有这条 JD → 先按 `jd-analysis` 把原文拿到并入库再来找面经。
不然你不知道该搜哪个岗位名，搜出来的面经大概率不是同一个岗。

### 2. 从 businessSkills 决定搜什么

`businessSkills` 是系统在 JD 入库时**从原文自动抽取**的技术方向标签（每条最多 5 个，
按 标题×5 > 技能字段×3 > 要求×2 > 描述×1 加权命中；界面里 JD 卡片上的彩色标签就是它）。
**你只读它，不要手写**——它代表这条 JD 真实的技术方向，比你自己概括的准。

它决定面经往哪个方向搜：同样是"算法工程师"，`rag` 和 `recsys` 的面经完全不同。

| businessSkills 标签 | 面经该搜的技术方向 |
|---|---|
| `rag` / `vector-search` | 检索增强、向量库选型、chunk 策略、召回率与 rerank 评测 |
| `agent-engineering` / `multi-agent` / `agent-memory` | Agent 框架、工具调用、任务规划、多智能体编排、幻觉控制 |
| `agent-rl` / `alignment-rlhf` / `reasoning-model` | RLHF/DPO/GRPO、奖励模型、偏好数据、长思维链 |
| `llm-post-train` / `llm-pretrain` / `model-distill` | SFT/LoRA、数据配比、分布式训练、蒸馏压缩 |
| `llm-inference` / `model-quant` / `train-infra` | vLLM/SGLang、KV Cache、量化、显存与吞吐优化 |
| `multimodal-video` / `multimodal-image` / `speech` | 视频与图像理解、VLM 训练、时序建模、语音链路 |
| `backend-dev` / `distributed` / `high-concurrency` / `middleware` | 语言与框架八股、分布式一致性、缓存与消息队列、性能调优 |
| `database` / `cloud-native` / `sre` | MySQL 索引与事务、K8s、监控告警与故障排查 |
| `recsys` / `search-rank` / `advertising` / `risk-control` | 召回排序、特征工程、A/B 实验、业务指标 |
| `data-pipeline` / `realtime-compute` / `data-governance` | SQL 与数仓建模、Flink/Spark、数据质量 |

多条标签就取**权重最高的 2-3 个**分别搜一轮。
`businessSkills` 为空或明显不对（JD 原文太短）→ 用 JD 的 `skills[]` 字段代替。

### 3. 构造检索词

首轮用最朴素的组合，再按结果迭代：

| 轮 | 查询模板 | 拿到什么 |
|---|---|---|
| 1 | `"<公司> <岗位> 面经"` | 主干面经 |
| 2 | `"<公司> 算法岗 一面 面经 2025"` | 最近某轮的具体题目 |
| 3 | `"<公司> 面试 流程 几轮"` | 轮次、形式、周期 |
| 4 | `"<公司> <技术栈> 面试题"`（技术栈取 §2 表，如 vLLM / RAG / Redis） | 该方向的专业题 |
| 5 | `"<公司> <岗位> 凉经"` / `"<公司> 面试 挂了"` | 失败复盘——哪一轮挂、为什么，往往比成功帖写得更细 |

**结果薄时按顺序降级：**

1. **换口语表达**：面经不一定标题带"面经"二字——`"<公司> 面试 难吗"`、
   `"<公司> 几轮面试"`、`"<公司> 值得去吗 面试"`。
2. **加时间词**：`2025`、`2026 届`、`秋招`/`春招`/`暑期实习`（校招和实习是两套面经）。
3. **放宽岗位**：去掉岗位词只搜公司；或换同义岗位名（"大模型算法工程师" ↔ "LLM 算法" ↔ "AI 应用开发"）。
4. **同类岗位类比**：搜同赛道同规模公司的同类岗位面经，
   **必须标注"这是同类岗位类比，不是该公司面经"**，不能混进正文当事实。
5. **兜底**：都不行 → 如实说"没找到面经"，转 §7 给标注为推断的建议，
   并提示用户从熟人、学院群、求职群里补一手信息。

**同一轮 2-3 条查询并行发出更快。** 别用同一个词反复搜。

### 4. 真读原文，别只看搜索摘要

搜索结果的标题/摘要常与正文不符（"面经"帖里可能只有一句吐槽）。
**筛出 3-5 篇最像面经的，用 `web_fetch` 逐篇读完**再下结论：

| 站点 | 特点 | 读法 |
|---|---|---|
| 牛客网 nowcoder | 校招面经主力，分轮次写得细 | 优先读；标题常是"公司+岗位+时间" |
| 知乎 | 长复盘，含流程、体验、薪资观感 | 读高赞长答；注意可能是几年前的 |
| 一亩三分地 | 大厂与海外，流程与 timeline 详细 | 部分板块要积分/登录 → 读不到就放弃 |
| 掘金 / CSDN | 技术题整理，常带答案 | 题目可用，但搬运多、时效差，必须交叉验证 |
| 小红书 | 时效新（校招/实习），碎片化 | 只看流程与体感，情绪化内容不当证据 |
| 脉脉 / 看准网 | 职场口碑、面试评价 | 匿名多、情绪重，只作参考信号 |

读的时候**记下出处**：站点 + 链接 + 大致发布时间（发帖时间比"我最近面的"这种模糊说法可信）。
页面要登录/付费、或抓不到正文 → **不绕过、不猜内容**，换一篇或换来源。

### 5. 抽取结构化摘要

读完后按固定字段抽——**只写原文里真有的**，没有就写"未提及"：

| 字段 | 抽什么 |
|---|---|
| 面试轮次与流程 | 几轮、什么形式（笔试/一面/二面/交叉面/HR）、每轮多久 |
| 各轮考察重点 | 一面偏基础还是项目？哪轮写代码？哪轮问业务与场景设计？ |
| 高频考点/题目 | 具体题目，标注"几篇提到" |
| 岗位技术栈相关问题 | 对应 §2 的方向（如"向量检索怎么评测"、"KV Cache 怎么优化"） |
| 面试官风格 | 追问深度、是否打断、是否让手推公式或现场写代码 |
| 时间线 | 投递 → 笔试 → 面试 → offer 各隔多久 |
| 笔试 | 有没有、几道题、什么平台、难度 |
| 负面反馈/坑点 | 流程拖、HR 沟通差、要求与 JD 不符、口头 offer 变卦 |

抽完先自检一遍：**每条都能指出是哪篇面经说的吗？** 指不出的删掉。

### 6. 交叉验证与时效标注

**至少 2-3 个独立来源**才能当结论用。每条信息后面带标注：

| 标注 | 含义 |
|---|---|
| ✅ 多源一致（N 篇） | N≥2 篇独立面经说法一致，可信度最高 |
| ⚠️ 单一来源 | 只有 1 篇提到，可能只是那个面试官的偏好 → 明说 |
| ⏳ 可能过期（YYYY.MM） | 发布距今超过 1 年，流程与技术栈都可能变了 |
| ❓ 未找到 | 所有来源都没提 → 写"未找到相关信息"，不要补一个"应该会问" |

**"独立"指不同作者的不同帖子。** 同一篇被转载到多个平台算一篇，同一作者的系列帖算一篇。
别把搬运当交叉验证。

### 7. 回接画像，给个人化的准备清单

这是本技能的价值所在：**面经只有落到"你"身上才有用。**

```
career_read({ kind: 'profile', confirmedOnly: true })   ← 已确认的技能/经历/短板
career_read({ kind: 'skills' })                          ← 已在学的，避免重复建议
```

把「面经高频考点 × 用户画像」分三类：

- **他有证据的**（项目/实习里做过）→ 提示会被深挖，要准备讲清细节并扛住追问；
- **他声称但无证据的**（简历写了没项目支撑）→ 提示容易在面试里被戳穿；
- **他完全没有的** → 真正的 gap，按「面经出现篇数 × 岗位相关度」排优先级。

带具体指涉，例如：

> "你简历里有 RAG 项目，但三份面经都提到会深挖向量检索的召回率优化——
> 这块建议准备：怎么评测召回、chunk 怎么切、rerank 上没上、指标提升了多少。"

不要写"建议复习项目细节"这种放之四海皆准的话。

### 8. 落到准备清单（要先问用户）

输出一份**有序**的准备清单，每项说清：**准备什么 / 为什么是它（面经依据 + 你的画像）/ 大概投入多久**。
优先"面经里反复出现 + 你现在最缺"的，而不是"听起来最厉害"的。

用户可能希望把这些缺口排进学习路线：

```
career_write({
  action: 'add_skill',
  confirmed: true,                    ← 必须先问过用户
  skill: {
    name: '向量检索评测',
    difficulty: 'medium',
    proposedBy: 'ai',
    reason: '目标岗位 5 篇面经中 3 篇深挖召回率优化，且用户画像里没有相关技能'
  }
})
```

**铁律：先问，再写。** 由面经推断出的缺口属于隐式推断，未经用户确认不得写入他的技能清单。
原话示例："3 篇面经都问了向量检索怎么评测，你这条现在没有。
要不要加进技能清单？我按中等难度给你排期。"——等他同意后再写。

**一次只加 2-3 个**，加 10 个等于没加（同 `learning-path`）。

## 输出格式

检索完成后按这个结构输出，**照抄框架、只填真实读到的内容**：

```markdown
## <公司> · <岗位> 面经调研

**检索**：共 N 条查询（列出主要检索词）
**读到并采信**：N 篇 ｜ **覆盖时间**：YYYY.MM ~ YYYY.MM
**来源**：① <站点> <链接>（YYYY.MM） ② … ③ …

### 1. 面试流程（N 篇交叉）
| 轮次 | 形式 | 时长 | 考察重点 | 来源数 |
|---|---|---|---|---|
| 笔试 | 在线机考 | 2h | 3 道算法题（中等偏难） | 4 篇 |
| 一面 | 视频 | 45min | 项目深挖 + 基础八股 | 5 篇 |
| 二面 | 视频 | 60min | 场景设计 + 业务理解 | 3 篇 |
| HR 面 | 电话 | 20min | 意向、薪资、到岗时间 | 2 篇 |

### 2. 高频考点（按出现篇数排序）
| 考点 | 出现 | 来源 | 时间 |
|---|---|---|---|
| 向量检索召回率怎么评测 | 3/5 | ①②⑤ | 2025.03-2025.09 |
| 项目里最大的技术难点 | 5/5 | ①②③④⑤ | 2025.03-2025.09 |

### 3. 时间线（投递 → offer）
- 均值约 X 周，最慢 Y 周（来源 ③，⚠️ 单一来源）

### 4. 结合你的画像：准备优先级
| 优先级 | 要准备什么 | 依据（面经 + 你的画像） | 投入 |
|---|---|---|---|
| P0 | 向量检索评测（召回/rerank 指标） | 3 篇面经深挖 + 你简历有 RAG 项目但无评测描述 | 2 天 |
| P1 | … | … | … |

### 5. 信息可靠性
- ✅ 多源一致：…
- ⚠️ 单一来源：…
- ⏳ 可能过期：…
- ❓ 未找到：…

### 6. 下一步
- 要不要把 P0 这两项加进技能清单？（需要你确认）
```

**一篇都没找到时**，如实说明，并把第 4 部分改成下面这样：

```markdown
### 4. 结合你的画像：准备优先级（⚠️ 以下为推断，非面经）
> 本轮检索没找到可靠面经。以下依据是 JD 要求 + 通用面试规律，
> 请当作准备方向的参考，**不要当成本公司的真题**。
```

## 边界与禁忌

- ❌ **不绕过登录/付费墙。** 面经帖要登录、要积分、要付费才能看的，放弃它换来源；
  不抓取登录后内容，也不用零散片段脑补正文。
- ❌ **不把一篇匿名帖当事实。** "据说这家面试很难"不是结论：要么有多源支撑，要么标注单一来源。
- ❌ **不拿负面评价吓用户。** 差评常是特定部门、特定时期的个案；转述要带语境
  （几篇里的几篇、什么时候、哪个部门），并加限定"这只是别人那次的体验"。
- ❌ **不忽视口径差异。** 面经可能是**别的团队、别的职级、别的年份**的：
  校招 ≠ 社招，实习 ≠ 正式，算法岗 ≠ 工程岗。对不上就明说"这份面经和你的岗位口径不同"。
- ❌ 不把同类公司的面经当成本公司面经（要标注是类比）。
- ✅ 顺序永远是：**先检索、先读原文，再下结论**。不允许跳过检索直接凭 JD 编面试题。

## 输出纪律

- ✅ 每条结论后面能指出来源（第几篇 / 链接 / 时间）。
- ✅ 查不到就如实说"没找到面经"，然后**明确标注**转为推断。
- ✅ 来源数与时效一起给（如"✅ 多源一致（3 篇，2025.03-2025.09）"）。
- ✅ 准备清单要排序、要具体、要跟画像对得上。
- ❌ 不编题、不编流程、不编时间线。
- ❌ 不写"复习基础、准备项目介绍"这类没有信息量的建议。
- ❌ 未经用户确认，不写入技能清单或投递。

## 衔接

- 这条 JD 还没入库 / 想先拆解要求 → 交接 `jd-analysis`（先拿到 JD 原文，再找面经）。
- 面经暴露的 gap 要排学习路线与考核 → 交接 `learning-path`（本技能只提缺口）。
- gap 牵涉简历写法（写了但没证据）→ 交接 `resume-review`。
- 用户还没把该岗位加入投递 → **先问**，确认后再用 `add_application` 写入。
