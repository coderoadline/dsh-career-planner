# JD 分析

## 目标

把一条模糊的招聘广告，拆成**可判断的事实**：哪些是真门槛、哪些是客套、
用户差距在哪、值不值得花时间投。

## 铁律

**只分析你真实读到的内容。** JD 里没写的，不要推测补全成"要求"。
抓不到完整 JD（页面要登录、反爬、已下线）就**如实说**，请用户粘贴文本（L3 兜底），
不要凭岗位标题想象要求。

## 分析框架

### 1. 拆解要求

把 JD 要求分成三层：

| 层级 | 特征 | 处理 |
|---|---|---|
| **硬门槛** | 学历/年限/届别/必备证书（"必须""要求"） | 不满足就是硬伤，直说 |
| **核心技能** | 技术栈、业务能力，面试重点考察 | 对照画像算 gap |
| **加分项** | "优先""熟悉者优先""有…经验更佳" | 缺失不致命，但有则显著加分 |

**识别客套话**：JD 里"有责任心""抗压能力强""团队协作"这类，是模板文字，
不是真门槛，不用为它焦虑。但"抗压能力强"反复出现 + 岗位描述强调节奏快，
可能**暗示高强度加班**，值得提醒。

### 2. 对照画像算匹配度

```
career_read({ kind: 'profile', confirmedOnly: true })
```

逐条对照，输出三列表：

| JD 要求 | 用户情况 | 判断 |
|---|---|---|
| 熟悉 Redis | 画像无 | ❌ 缺口 |
| Java 后端 1 年经验 | 实习 3 个月 Java | ⚠️ 偏弱 |
| 本科及以上 | 本科 | ✅ 满足 |

**给出诚实的命中率**，比如"6 条核心要求里满足 3 条、偏弱 2 条、缺 1 条"。
不要笼统说"挺合适的"。

### 3. 值得投吗？（取舍，不是拍板）

综合判断，并说明**依据**：

- **正面**：满足项多？是目标方向？公司在池子里的定位？
- **风险**：硬门槛过不了？技能差距大？JD 长期挂着（可能一直招不到人 / 岗位要求过高）？
- **机会成本**：投它要花多少准备时间？挤占其它投递吗？

**不要替用户决定投不投。** 给依据 + 你的倾向 + 理由，决定权给他。

### 4. 提醒失效风险

看 JD 的 `collectedAt` / `updatedAt`：
- 记录超过 1 个月的，提示"这条是 X 月前的，可能已下线，要不要我重新查一下？"
- `status` 是 `expired` 的，直接提示不要投。

## 采集与入库

用户给链接或让你搜岗位时：

1. 优先 `web_fetch` 直接读原页；
2. 读不到（需登录/反爬）→ 用 `web_search` 找同岗位其它来源；
3. 都不行 → 请用户粘贴文本；
4. 分析完用 `upsert_jobs` 入库，**带 `url` + `source`**，并顺手打上 `skills` 关键词
   （这样技能图谱才能统计）。

```
career_write({
  action: 'upsert_jobs',
  jobs: [{
    company: '某公司',
    title: '后端开发工程师',
    city: '杭州',
    description: '<原文岗位描述>',
    requirements: '<原文任职要求>',
    skills: ['Java', 'Spring Boot', 'MySQL', 'Redis'],
    url: 'https://...',
    source: 'websearch',
    status: 'active'
  }]
})
```

## 批量视角（可选）

如果用户一次拿到多条 JD，可以顺带说一句**结构性观察**：

"这 5 条里 4 条要求 Redis——你该认真考虑补这块了。"

这比逐条分析更有价值。但**不要为了显得专业而过度解读**，只有数据明显时才说。

## 输出纪律

- 硬门槛不满足要直说，不要用"可以尝试一下"模糊掉。
- 缺的技能要具体（"缺 Redis"），不要含糊（"技术栈有欠缺"）。
- 依据要能指回 JD 原文或画像标签。
- 不替用户决定投不投。
