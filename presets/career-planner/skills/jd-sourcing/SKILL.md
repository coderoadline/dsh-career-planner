# 岗位检索与入库

## 一句话

**从「用户想要什么」出发，去公开渠道捞回真实、可投、能核实的岗位，写进 JD 池。**

JD 池是后面一切分析的证据基础：方向可行性、匹配度、学习优先级，
全都建立在"市场上真实存在的岗位"上。**池子里是假数据或过期数据，结论就是错的。**

## ⛔ 第一条铁律：先确认，再检索

**不要一上来就搜。** 方向错了，搜得再勤也是白费——用户不会因为你搜了 20 个岗位就满意，
他只会因为"这些都不是我想投的"而失望。

开始检索前，**一次问完**这几个高杠杆问题（能自己查到的别问，画像里有的别问）：

| 问什么 | 怎么问 | 为什么必须问 |
|---|---|---|
| **方向** | "我基于你的画像看到这几条路：A / B / C。想找哪几个？或者你自己有别的想法？" | 方向决定搜索词。**必须给候选 + 留自填口**，别让用户凭空想 |
| **公司层级/类型** | "想投哪一类：行业头部 / 成长型 / 垂直细分 / 外企 / 公共部门与事业单位？" | 决定检索范围，见下方「分层取样」 |
| **地点** | 画像里有就直接用，没有才问 | 过滤条件 |
| **硬门槛** | "有没有不能妥协的？比如只做某类岗、必须能转正、必须在某地" | 避免找回来一堆注定被排除的 |

追问要克制：**一次问完，不要边找边问**。用户答不上来的（比如"我也没想清楚方向"），
就按画像给默认建议并说明"我先按 X 找，不合适随时换"。

> 📌 这条与 `career-profile` 的「一次问一个主题」**不冲突**，两者管的是不同场景：
> 那条约束的是**日常闲聊式采集**（别把聊天变成审讯）；
> 这条管的是**任务启动前的确认**（问错了后面全白干，所以一次问清）。
> 判据：**问错了会让后面白费功夫的，就现在问完。**

## ⛔ 第二条铁律：JD 字段只放原文，不掺你的话

`description` / `requirements` / `title` 是**证据字段**。它们会被用来算匹配度、
做方向统计、准备面试——**掺进你自己的话，后面每一个结论都跟着脏**。

### 唯一允许的写法：原文照录

- 原文怎么写就怎么写，**包括它自己的分节**（`岗位职责` / `岗位基本要求` / `岗位亮点`）。
- 原文里的数字、日期、批次号、职位 ID，一个不改、一个不漏。
- 标题用**岗位原名**。两个岗位同名就同名，**不要为了区分自己加后缀**。

### 明确禁止

| 禁止 | 反面例子 | 为什么 |
|---|---|---|
| **加推断** | 原文没写届别 → 你写"不限届别" | 你没看到 ≠ 不存在。这是**编造事实** |
| **加判断** | `（不卡届别，2028 届可投）`「（门槛低）」「（建议优先投）」 | 判断是你的输出，不是 JD 的属性 |
| **加评价** | `（团队很强）`「（业务前景好）」 | 你无从核实 |
| **加归属** | 原文没提的部门 / 团队，自己补上去 | 同上 |
| **加后缀** | 标题写成 `大模型算法实习生（后训练方向）` | 岗位名只有一个 |
| **写过程** | `source` 写成 `XX 官网（实访核实，ID=123）` | `source` 只写来源站点 |

### 真实翻车案例（这条规则的由来）

一条岗位原文写着「**2026 届获得本科及以上学历**」。
我在它的描述开头加了「（不卡届别，2028 届可投）」——**纯属我自己的推断，而且推错了**。

用户是 2028 届。结果：我把一条**他根本投不了的岗位**标成"可投"，
还基于这个错误结论推荐他优先投。

**推断混进事实字段，比字段空缺危险得多**——它会顶着"事实"的身份，
进入后续每一次决策，而用户永远不会想到去质疑它。

### 那你的判断放哪

| 内容 | 放哪 |
|---|---|
| 岗位**方向** | `skills` 标签字段（这本来就该是你的判断） |
| 门槛是否匹配、值不值得投、有什么风险 | **你的回复里**，说给用户听 |
| 来源 | `source`，只写站点名，如 `美团招聘官网` |

**原文没写的，就当它没写。** 如实说"这条 JD 没提届别"，
而不是替他推断成"不限届别"。

## 检索手段：用当前可用的能力，别写死工具

**你需要的能力是这三件事**，用什么达成不重要：

1. 能搜到公开的岗位信息；
2. 能打开岗位详情页、读到完整正文（职责 + 要求 + 地点 + 类型）；
3. 能拿到该岗位的可访问链接。

**可用手段（按当前环境有什么就用什么）：**

- 内置的联网搜索能力；
- 浏览器自动化能力（若环境提供）；
- 用户直接给的链接、截图、粘贴的 JD 文本；
- 招聘平台的公开页面或接口。

**原则：哪条路通走哪条；某条路不通就换，并且告诉用户你换了。**

```
❌ "只能用某个特定工具" —— 工具会变，流程不该绑死在工具上
✅ "需要能联网检索 + 读详情页 + 取链接，用当前环境提供的任何手段达成"
```

**站点不可用不是失败，静默跳过才是。** 遇到打不开、筛选失效、内容乱码，
记录一句"XX 站点不可用，原因：筛选参数无效"，继续下一个。**最后要汇报。**

## 分层取样：别只在熟人堆里找

⚠️ **最常见的失误：只搜画像里已经出现过的那几家公司。**
用户池子里有 A 和 B，不代表他只想投 A 和 B —— 那通常只是他随手存的。

**强制要求：至少覆盖 3 个不同层级/类型的雇主。**

| 层级 | 说明 | 典型 |
|---|---|---|
| 行业头部 | 大厂、龙头、知名机构 | 规模大、流程长、简历门槛高 |
| 成长型 | 融资中期的公司 | 机会多、要求灵活、成长快 |
| 垂直细分 | 某个细分领域的专业公司 | 门槛聚焦、对口度高 |
| 外企 / 合资 | 跨国企业 | 语言要求、流程规范 |
| 公共部门 / 事业单位 / 国企 | 体制内 | 招考节奏、专业限制 |
| 中小微 / 初创 | 小团队 | 上手快、职责宽 |

不同层级对同一个人意味着完全不同的机会和代价——
只推头部会让用户误以为"我够不上任何岗位"，只推小公司又会低估他的上限。
**分层的意义是让用户看到自己的真实可选空间。**

## 核实：URL 与岗位必须成对确认

⚠️ **真实翻车案例**：同时开了多个岗位详情页，凭记忆把 URL 配给了错误的岗位，
结果入库的"后训练岗"链接指向"服务智能岗"。**用户点进去会发现货不对板。**

**铁律：每一条入库的 URL，都必须是"你刚刚在那个页面上读到的岗位"。**

```
✅ 正确：打开页面 → 读标题和正文 → 立刻取当前页 URL → 成对记录 → 入库
❌ 错误：批量开 5 个页面 → 读完全部内容 → 凭记忆配对 URL 和岗位
```

多个岗位并行处理时，**一个岗位走完"读内容 → 取 URL → 记录"再开下一个**，
或者逐条打开验证。宁可慢一点，也不要配错。

### 拿不到 URL 时的分级策略

按代价从低到高试：

1. **标签页/窗口列表** —— 很多环境能直接列出已打开页面的标题与 URL，最省事，优先试这个；
2. **页面内的链接** —— 从列表页的 `href` 直接取；
3. **截图 + 视觉识别** —— 截图地址栏交给能看图的模型读。⚠️ 注意**长 URL 会被截断**，
   读取后要与页面标题交叉验证；环境不具备读图能力时跳过这条；
4. **兜底** —— 确实拿不到就用「公司 + 岗位名 + 来源站点」作为标识入库，
   并在 `source` 里注明「链接待补」，**不要编造 URL**。

**永远不要编造或猜测链接。** 一个假链接比没有链接危害大得多。

## 入库

### 去重：只跳过"完全同一个岗位"

⚠️ **不要把"方向相似"当成重复。**
同一个方向下的多条 JD 是有价值的——它们共同告诉你这个方向在市场上有多热、
要求有多一致、门槛区间在哪。删掉它们等于丢掉了市场信号。

```
✅ 跳过：同一公司 + 同一岗位名 + 同一团队/部门  → 确实是一个岗位
❌ 别跳：同公司不同岗位（"大模型算法实习生" vs "大模型评测实习生"）→ 两个岗位，都要留
❌ 别跳：不同公司的同类岗位 → 保留，这是横向对比的依据
❌ 别跳：同公司同方向但不同批次/地点 → 保留
```

**入库前先读一次 JD 池**，确认你要加的确实是新岗位，而不是同一岗位换个写法。

### 必须记录的字段

| 字段 | 要点 |
|---|---|
| `url` | 必填。必须是你**读过的那一页的真实链接**，不得猜测、不得编造 |
| `source` | **只写来源站点**，如 `美团招聘官网`。不写核实过程、不写 ID、不加括号注解 |
| `skills` | **方向标签**，1~5 个，先读词表复用。⚠️ 别把通用技能词当方向，见 `jd-tagging` |
| `description` | JD 正文**原文照录**，见上方「第二条铁律」 |
| `requirements` | 原文的「任职要求 / 岗位基本要求」照录，**不要改写成摘要** |
| `city` / `salary` | 照原文。原文没写就留空，**不要填"面议"之外的猜测** |
| `title` | 岗位原名，不加后缀 |

### 招聘类型 / 届别 / 投递约束：原文有才记，没有就不写

这三项对决策最重要，但也最容易被我"顺手补上"——**补就是错**。

| 情况 | 正确做法 |
|---|---|
| 原文写了（如「2026 届本科及以上」「最多投 3 个职位」） | **照录进 `description`**，它本来就在原文里 |
| 原文没写 | **什么都不写**，在回复里如实说"这条没提届别" |

**绝对不要**：

- ❌ 原文没写届别 → 写成「不限届别」「不卡届别」
- ❌ 原文没给可投数量 → 自己推断"应该不限"
- ❌ 把届别结论写进 `title` 或 `source`

**缺信息本身就是有价值的信号**——它意味着你得去问 HR，
而不是意味着"默认不限制"。

顺带：招聘页上这些规则往往比岗位要求更能决定策略，所以要**找全**——
截止日期、可投岗位数上限、流程互斥规则（如"同一时间仅 1 个流程进行中"）、
志愿顺序、到岗要求、特殊前置条件（如"须征得导师同意"）。

**找全是你的职责；编造不是。**

## 汇报纪律

检索完成后，**必须交代四件事**，缺一不可：

1. **找到了什么** —— 岗位清单，含层级分布；
2. **覆盖了哪些渠道** —— 别只说结果，说清来源范围；
3. **失败了什么** —— 哪个站点/渠道没走通、为什么、你换成了什么。**不许静默跳过**；
4. **排除了什么** —— 看了但不合适的，一句话说明原因
   （如"要求英语专业，与用户背景不符"），让用户知道你没漏掉它。

**为什么要汇报失败**：用户看不到你的过程，只看得到结果。
如果字节搜不动、你悄悄换了美团，用户会以为"字节没有合适的岗位"——
而事实是"字节没搜成"。**这两种结论对决策的影响完全不同。**

## 跨行业通用

这套流程不限技术岗。产品、运营、设计、金融、医疗、教育、制造、公共部门……
全都适用，只是搜索词、渠道、门槛字段不同。

| 行业 | 方向标签举例 | 特殊门槛举例 |
|---|---|---|
| 技术 | 大模型后训练 / 推荐系统 / 后端开发 | 语言版本、技术栈、论文 |
| 产品 | 用户增长 / B 端产品 / 商业化 | 作品集、行业理解 |
| 金融 | 风控与反欺诈 / 量化研究 | 从业资格证、院校门槛 |
| 设计 | 交互设计 / 品牌视觉 | 作品集质量 |
| 医疗 | 临床研究 / 药物警戒 | 执业资质、规培 |
| 公共部门 | 综合管理 / 专业技术 | 户籍、专业目录、招考时间窗 |

**不确定某个行业的门槛字段？** 那就去找——这正是检索要解决的问题。
不要因为"我不懂这个行业"就跳过核实，也不要把技术岗的判据套到别的行业上。

## 输出纪律

- ❌ 不先问方向就开始大搜
- ❌ 不只在画像/JD 池已出现的公司里找
- ❌ 不凭记忆配对 URL 与岗位
- ❌ 不编造链接
- ❌ 不把"方向相似"当重复去重
- ❌ 不静默跳过失败的渠道
- ❌ 不把通用技能词（Python、沟通能力）当成方向标签
- ❌ 不在 `description` / `requirements` / `title` / `source` 里掺自己的判断、推断、评价、后缀
- ✅ 一次问完关键问题再开工
- ✅ 覆盖 ≥3 个雇主层级
- ✅ 每个岗位"读内容 → 取 URL → 记录"成对完成
- ✅ 招聘类型 / 届别 / 投递约束：**原文有则照录，没有就不写、不推断**
- ✅ 汇报覆盖范围、失败项、排除项

## 衔接

- 拿到 JD 后的方向可行性判断 → `direction-advice`
- 单条 JD 的匹配度与门槛分析 → `jd-analysis`
- 打标规则与词表维护 → `jd-tagging`
- 根据缺口排学习计划 → `learning-path`
