# JD 打标与词表维护

## 一句话

**`skills` 字段就是这条 JD 的技术标签。** 不是两个东西，不需要二次动作。

界面上每条 JD 显示的彩色气泡、图谱里的「方向热度」、点一下筛出同类 JD 的那份，
读的都是 `skills`。所以你录入 JD 时把方向写进 `upsert_jobs` 的 `skills`，
一次就到位 —— **别先录进去再单独跑一次打标**，那时你已经读过这份 JD 了，
多一轮纯属浪费。

## 目标

把每条 JD 归到**它真正的方向**上（`大模型后训练`、`Agent RL`、`多模态视频理解`、
`用户增长`、`供应链管理`…），并让这套方向词表随着 JD 越用越贴合用户实际在看的市场。

这套标签是后面所有分析的地基：技能图谱靠它聚合、差距分析靠它算、
"这个方向岗位多不多"靠它统计。**标错了后面全错**，所以宁可少标、标准。

## 铁律

1. **只标你真实读到的内容。** JD 里没写的方向不要推测补全。
2. **不要为了"看起来有标签"硬凑。** 一条 JD 实在只体现一个方向，就只给 1 个。
3. **录入即打标** —— 单独调 `tag_job` 只用于下面那两种情况。

## ⚠️ 陷阱一：方向标签 ≠ 通用技术词

**`skills` 是「方向」，不是「技能清单」。** 这是最容易标错的地方。

真实翻车案例：给一条**大模型评测实习生**打了 `Python` 和 `深度学习基础`。
问题不只是"标偏了"——`Python` 是**所有**技术岗都写的通用要求，
它对"这条 JD 属于什么方向"零信息量；而这条 JD 真正的方向是「大模型评测」，
却因为词表里没有这个词，**整条 JD 最值钱的那个信号没被记下来**。
后果：后续按方向聚合、算匹配度、看热点时，**用户最强的那块能力在图上根本看不见**。

| 该标（方向） | 不该标（通用技能/软素质） |
|---|---|
| `大模型评测`、`大模型后训练`、`推荐系统` | `Python`、`PyTorch`、`SQL` |
| `风控与反欺诈`、`用户增长`、`B 端产品` | `沟通能力`、`团队协作`、`学习能力强` |
| `语音大模型`、`Agent RL`、`信息抽取` | `英语读写`、`Office`、`责任心` |

**判据：把这条 JD 换个方向，这个词还会出现吗？**
会 → 它是通用技能，不标。不会 → 它是方向，标。

**词表里没有合适的？那就加。** 这正是词表成长的途径。
⚠️ 但加之前先想清楚：**这个词是"这个岗位的方向"，还是"这个岗位用到的工具"？**
后者不要加进词表——否则词表会被 `Python`、`Excel` 这类词污染，
而它们对所有方向都适用，等于噪音。

**连带动作**：标完检查一遍——**这条 JD 最核心的方向，词表里有对应词吗？**
如果没有，而这条 JD 又对用户很重要（比如正是他的强项方向），
那就把这个方向词补进词表。**别让用户最强的能力在标签体系里没有名字。**

## ⚠️ 陷阱二：`skills` 里写对象会被压成 `[object Object]`

数据层对 `skills` 的每一项做字符串归一。早先的实现是无条件 `String(raw)`，
于是 `{ label: '大模型后训练', aliases: ['LLM Post-training'] }` 会被压成字面量
**`"[object Object]"`** —— 界面、图谱、筛选全部拿到一个叫 `[object Object]` 的假技能。

该缺陷已在数据层修复（对象形式会正确取 `label`，并把 `aliases` 用于归并），
但**你仍然应该优先写字符串**：

```js
// ✅ 推荐：纯字符串，最稳
skills: ['大模型后训练', 'Agent RL']

// ⚠️ 仅在需要显式指定别名时用对象
skills: [{ label: '智能体强化学习', aliases: ['Agent RL'] }]
```

**入库后回读校验**：`career_read({ kind: 'jobs' })`，
确认没有 `[object Object]` 这种标签出现。有就是踩坑了，删掉重写。

## 流程（录入时，一次调用）

```
career_read({ kind: 'taxonomy' })     ← 先看已有词表，这一步不能跳
career_write({ action: 'upsert_jobs', jobs: [{
  company, title, city, url, source, requirements, description,
  skills: ['语音大模型', '度量学习'],  ← 标签就写在这里
}]})
```

为什么第一步不能跳：词表是活的，里面既有历史数据带过来的词，也有你之前打标新增的词。
跳过它就会重复造词，同义词一多，图谱就散成一片。

## 判方向：看它实际要做什么

| 该标 | 不该标 |
|---|---|
| 岗位标题里的方向（`算法实习生-抖音研发` → 语音/音频方向） | 团队介绍里顺带提的产品名 |
| 任职要求里明确要求的技能（`熟悉 vLLM 推理加速` → 推理加速与部署） | "需与算法同学沟通协作" → 不等于算法岗 |
| 岗位职责的核心动作（`负责推荐召回链路` → 推荐系统） | 一句"了解深度学习基础"这种客套要求 |

判据：**面试官会因为这个方向来考你，那才算这条 JD 的方向。**

## 复用优先，再考虑新增

复用规则（大小写、空格、全角都不敏感）：

- 你写的词命中词表里任何词的 label 或 aliases → **算复用**，系统自动归并到同一条；
- 你更习惯另一种叫法 → 把它放进 `aliases`，系统会记下来，下次别人这么写也不会分裂。

```
{ label: '度量学习' }                              ← 词表已有，复用
{ label: '智能体强化学习', aliases: ['Agent RL'] } ← 换了叫法，给 alias 让系统归并
```

反例：

```
{ label: 'RAG 相关技术' }    ❌ 词表已有 RAG，这是同义改写，会造出重复词条
{ label: '大模型' }          ❌ 太宽，等于没标
```

### 数量与语言

- **1~5 个**，按重要程度排序（最重要的放第一个）；
- **至少 1 个**：只要这条 JD 有实质内容就该有归属方向。
  真一个都定不出来，说明 JD 文本残缺 —— 那就去把 JD 读全，而不是随便贴一个；
- **词的语言跟系统界面一致**（当前中文界面 → 中文词）。
  英文专有名词（`RAG`、`Kubernetes`、`vLLM`、`Agent RL`）保持原样，不必硬翻。

## 非技术岗同样要标

这套机制不限技术岗。产品/运营/设计/金融/供应链都按**该行业自己的方向词**标：

| 岗位 | 合理标签 |
|---|---|
| 用户增长运营 | `用户增长`、`数据驱动运营` |
| 金融风控算法 | `风控与反欺诈`、`特征工程` |
| B 端产品经理 | `B 端产品`、`需求分析` |

词表里没有合适的？**直接加**，这就是词表成长的途径。但先确认过确实没有。

## 什么时候才用单独的 `tag_job`

只有这两种：

1. **用户在工作台手动录入、技能关键词留空的 JD。** 那条路上没有模型，所以标签是空的。
   工作台会显示「待 AI 分析」，用户点一下就把任务递给你。
2. **JD 正文被改过、标签已被系统作废。** 这时重新读那条 JD，把新方向写回去。

查哪些还没标签：

```
career-workbench API → pendingTagging      ← 没标签 / 标签已过期的 JD
```

⚠️ 它的返回里有 `suggestions` 字段（老关键词引擎给的提示）。
**那只是参考，不是答案** —— 它是被废弃的正则逻辑算出来的，经常抓偏
（比如把"移动端顺带一提"建议成方向）。以你读的 JD 正文为准。

批量处理时按公司或岗位族分组，同族口径要一致，
别这条叫「大模型后训练」那条叫「模型后训练」。

## 改正文的正确姿势

**同时改了正文和标签 → 写进同一次调用**，新标签会被采纳，不会被作废逻辑清掉。

只改正文不给标签时，系统会**作废原标签**并标记待重打标 —— 因为旧标签描述的不是
现在这份内容，留着就是错的。这时你必须重新读那条 JD 再写，
**不要沿用记忆里的旧标签**。

## 词表清理

发现词表里有同义重复（`多智能体协作` / `Multi-Agent 系统` 各挂 2 条 JD）：

1. 选一个保留（选引用多、叫法更通用的）；
2. `career_write({ action: 'merge_terms', fromId, intoId, confirmed: true })`；
3. 被合并的词自动变成保留项的 alias，引用它的 JD 一起改过去。

词表里 `count = 0` 且明显是误标的词，可以直接删。
**不要**因为"感觉以后用得上"就留着 —— 词表越干净，复用判断越准。

## 输出纪律

- ❌ 不为了凑数加标签；不确定就少标，不要标满 5 个
- ❌ 不跳过"先读词表"这一步
- ❌ 不把 `suggestions` 当答案照抄
- ❌ 不在技术岗上贴"沟通能力""抗压"这类软素质词
- ❌ 不"先录 JD 再单独打一次标"（除上面那两种情况）
- ✅ 打标后简短说明新增了哪几个词（让用户知道词表在怎么长）
- ✅ 发现同义重复时主动合并，而不是继续用新的
- ✅ 拿不准某条对不对时，说出来并给出你的判断依据

## 衔接

打完标之后：
- 方向分布与热点 → 用 `direction-advice`
- 具体某条 JD 的匹配度与门槛 → 用 `jd-analysis`
- 该学什么、怎么排优先级 → 用 `learning-path`
