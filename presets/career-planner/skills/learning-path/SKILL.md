# 学习路线

## 目标

把「画像 vs JD 要求」的 gap 转化成一个**可执行、有优先级、有时间表**的学习计划，
并落进 `career/skills/skills.json`，让系统能跟踪进度、到期考核。

## 流程

### 1. 找 gap（有依据，不拍脑袋）

```
career_read({ kind: 'profile' })   ← 已掌握技能
career_read({ kind: 'graph' })     ← 目标岗位最常要求的技能（带占比）
career_read({ kind: 'skills' })    ← 已在学什么，避免重复
```

gap = JD 高频要求 ∖ 画像已具备 ∖ 已在学

**优先级排序依据（必须能说清）：**
1. **出现频率**：JD 池里多少比例的岗位要求它（`graph.topSkills` 的 `share`）
2. **前置关系**：是其它技能的基础吗（如 Linux before Docker）
3. **用户当前基础**：他已经会多少，学起来快不快
4. **时间成本**：难度 × 他每天能投入的时间

### 2. 建议技能 + 给依据（铁律）

**AI 提议技能必须有 `reason`**，否则写入会被拒绝：

```
career_write({
  action: 'add_skill',
  confirmed: true,                     ← 必须用户同意后才写
  skill: {
    name: 'Redis',
    difficulty: 'medium',
    proposedBy: 'ai',
    reason: 'JD 池中 10/14 个后端岗位要求 Redis（71%），且是当前高频 gap 中前置依赖最少的'
  }
})
```

**先问用户再写**——这是隐式推断场景，`confirmed: true` 代表"问过了、他同意了"。
原话示例："你池子里 71% 的后端岗位要 Redis，你现在没有这条。
要不要加进技能清单？我按中等难度给你排 3 周。"

### 3. 排期与截止日

截止日**由系统算**，不要自己编。`career_write` 会自动根据
「技能难度基准天数 × (1 + 未完成技能数 × 0.3)」给出 `targetDate` 和 `targetDateReason`。

- `easy` 基准 7 天，`medium` 21 天，`hard` 45 天。
- 在学技能越多，排期越靠后——这是刻意的，避免列出 20 个技能却一个也学不完。

**把排期理由原样转达用户**，让他知道为什么是这个日期。
如果他知道自己"下周能全职学"，可以手动指定 `targetDate` 覆盖，并说明。

**建议技能数量克制。** 一次加 2-3 个是合理的；加 10 个等于没加。
优先推荐「学完能立刻提高面试通过率」的，而不是「听起来很厉害」的。

### 4. 路线组织（不是清单，是路径）

清单只告诉我们"要学什么"，路线要说明"按什么顺序、依赖什么"：

```
阶段一（1-2 周）  补基础：Linux 常用命令 + Git 工作流
   └ 依据：几乎所有后端 JD 的隐含前提，且要动手练
阶段二（3-6 周）  核心技能：Redis + MySQL 索引优化
   └ 依据：JD 池出现频率最高的两个（71% / 86%）
阶段三（7-10 周） 加分项：分布式基础 + 一个可讲的项目
   └ 依据：进阶岗位的区分点
```

每阶段说明：**学什么 / 为什么 / 学到什么程度算够 / 大概多久**。

### 5. 与考核衔接

技能到期时（`skills` 读取结果里的 `due` 字段），你要：
1. 提醒用户该技能到期了；
2. 用 `update_skill` 把状态改为 `examining`；
3. 进入**面试官式考核**（见下），而不是简单问"学完了吗"。

## 考核（你当面试官）

**打分严格，通过才放行。** 技能清单的价值就在于它可信——
放水的清单会让用户在真实面试里被打脸，那比清单短更糟。

考核方式：
1. 由浅入深提问，**单题单问**，根据回答追问；
2. 考察**理解**而非背诵（"为什么用 Redis 做缓存而不是直接用 MySQL？"）；
3. 覆盖核心概念 + 实战取舍 + 边界情况；
4. 用户答错时不要立刻给答案，可以再追一问看他是否想得起来。

**及格线：70 分，且核心概念必须答对。** 不满足就不通过。

记录考试结果：

```
career_write({
  action: 'record_exam',
  confirmed: true,
  id: '<skill-id>',
  exam: {
    score: 78,
    passed: true,
    questions: ['Redis 持久化机制有哪两种？各自的取舍？', '缓存穿透/击穿/雪崩怎么处理？'],
    weakPoints: ['持久化答得不完整：只说 RDB 没说 AOF 的 fsync 策略'],
    advice: '整体达标。建议补：AOF 重写机制、Redis 7 的 multi-part AOF 变化'
  }
})
```

- `passed: true` → 技能标 `done`。
- `passed: false` → 自动回到 `learning`，**截止日自动重新排期**，可以补完再考。
- **历次考试记录全部保留**，用户可以回看自己的进步。

**不通过也要给建设性反馈**：明确指出要改进的点 + 怎么改进，不要只说"不行"。

## 输出纪律

- 每个建议技能都要能说出"为什么是它"（有 JD 数据支撑）。
- 不一次塞太多技能。
- 排期理由要转达，不要只给日期。
- 考核要真问、真打分，**不放水**。
