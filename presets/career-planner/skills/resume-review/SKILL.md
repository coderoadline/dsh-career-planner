# 简历剖析

## 铁律

**只剖析和建议，绝不修改原件。**
`career/resumes/` 下的简历原件永不被本系统修改。你的输出是**建议**，
由用户自己决定改不改。解析结果只写到 `<文件名>.parsed.txt`。

原因：简历是用户最敏感的个人数据，任何"帮你自动优化"都可能
措辞失真、丢失他真实想表达的东西。

## 读取简历

```
career_read({ kind: 'resumes' })          ← 列出简历，看 hasParsed
read('career/resumes/<name>.parsed.txt')  ← 读解析文本
```

如果只有二进制原件（`hasParsed: false`）：
- 说明这是 PDF/DOCX，需要解析；
- 可以尝试用可用工具解析，或**建议用户把简历另存为 .md / .txt 再上传**
  （纯文本解析最可靠）；
- 解析成功后用 store 的 `saveResumeParsed` 思路落盘（不改原件）。

## 剖析框架

### 1. 提取画像标签（进待确认区）

从简历提取技能、经历、学历等，写入时：

```
career_write({
  action: 'upsert_tags',
  confirmed: false,              ← 关键：简历解析默认未确认
  tags: [{
    dimension: 'experience',
    label: '某公司后端实习',
    value: '3 个月',
    evidence: '简历原文：2025.07-2025.09 某公司 后端开发实习生',
    source: 'resume_parsed',
    confidence: 'high'
  }]
})
```

然后**逐条向用户确认**再升级为 `confirmed: true`。

**注意**：简历是给 HR 看的，有包装成分。不要把简历里的自述当成
确认过的能力——尤其"熟练掌握"这类没有项目支撑的表述，`confidence` 给低。

**⚠️ 场景 ≠ 技能（高频错误）**：**项目名/产品名不等于他本人做的技术工作。**
简历写「车载语音助手项目」，他可能只做了意图分类与 query 改写，从未接触语音/声学。
若照抄成技能「车载语音交互」，方向推荐会直接跑偏到语音多模态岗——面试第一个问题就露馅。

提取技能时逐条自问：**这个技能名，是来自项目名，还是来自他具体的工作描述？**
来自项目名的，**先问**：「这个项目里你实际负责哪部分？」得到答复再写。
（把用户答复写进 `evidence`，注明「用户澄清」，并同步修正已有的相关标签。）

| 简历原文 | ❌ 错误标签 | ✅ 正确标签 |
|---|---|---|
| 车载语音助手项目的意图理解与 query 改写 | 车载语音交互 | 意图理解与 Query 改写 |
| 电商平台的推荐算法优化 | 电商运营 | 推荐算法 |

### 2. 常见问题检查

| 维度 | 检查点 |
|---|---|
| **针对性** | 是否按目标岗位定制？还是海投同一份？ |
| **量化** | 经历是否只有职责没有成果？"负责后端开发" vs "优化接口响应时间 800ms→120ms" |
| **关键词** | 目标 JD 的核心技能，简历里有没有体现（**过 HR 筛选靠这个**） |
| **真实性** | 写的和画像里已确认的能力一致吗？有没有夸大？（夸大是面试杀手） |
| **结构** | 有无冗余、时间倒序、排版是否易扫读 |
| **篇幅** | 应届 1 页为宜 |

### 3. 对照目标 JD（最有价值的分析）

```
career_read({ kind: 'profile', confirmedOnly: true })
career_read({ kind: 'jobs', keyword: '<目标岗位关键词>' })
```

找出**目标岗位高频要求 vs 简历已体现**的差集：

- JD 要但简历没写的技能 → **补进简历**（如果真会）
- 简历写了但 JD 不要的 → 建议精简
- 简历写了但没有证据的 → 建议补项目或降低措辞

**这是简历修改的最高优先级**，比排版重要得多。

### 4. 给具体建议

❌ 不好："建议优化项目描述。"
✅ 好："第二段项目只写了'负责后端开发'。改成：
'独立完成订单模块 API 设计与实现，用 Redis 缓存热点数据把 QPS 从 200 提到 800'——
这样 HR 能一眼看到你的技术深度和量化成果。"

**给可直接使用的改写示例**，但标注"这是示例，请按你真实情况调整"——
**绝不鼓励编造**。如果某个技能他确实不会，应该说"这个技能你不会，
要么去学（我可以排学习计划），要么不写"。

## 输出纪律

- ❌ 不修改原件。
- ❌ 不鼓励夸大或编造经历。
- ❌ 简历解析的标签不自动确认为事实。
- ✅ 给具体的改写示例，而非笼统建议。
- ✅ 优先做「对照目标 JD 的差距分析」，其次才是排版措辞。
- ✅ 发现简历写了但画像中没有证据的技能时，主动问用户："这条是真的会吗？"
